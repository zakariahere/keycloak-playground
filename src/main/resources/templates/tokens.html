Token inspector

Three tokens came back from Keycloak. They look alike and do completely different jobs.

ID token Proof of authentication, addressed to this app. Answers “who logged in?”. Expires in 300s. Never send it to an API.
Access token Proof of authorization, addressed to an API. Answers “what may the bearer do?”. Expires in 300s. This is the one you put in Authorization: Bearer.
Refresh token Present (ey...). Long-lived, stays server-side, buys new access tokens without re-prompting you. Not issued.

Short access-token lifetime is deliberate. A stolen access token is only useful for about five minutes, because revocation cannot be enforced on a self-contained JWT — the API validates it offline and never phones home.

Spot the differences

audThe ID token is addressed to spring-web. The access token carries playground-api, added by an audience protocol mapper. Our resource server rejects anything without it.
realm_access.rolesKeycloak puts roles in the access token by default. They only appear in the ID token here because the realm adds an extra mapper for it.
typID vs Bearer. Keycloak labels them so a careful API can refuse an ID token outright.
kidSame in both: the same realm key signed them. Your app fetched the matching public key from /protocol/openid-connect/certs and cached it.

Call the API with this token

The server attaches the bearer header for you. The browser never sees the token.

GET /api/public GET /api/me GET /api/admin/report

Logged in as alice, the last one returns 403 — her token is valid, it simply does not carry app-admin. Authentication succeeded; authorization failed.
